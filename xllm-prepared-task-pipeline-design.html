xLLM Execution Architecture

PreparedTaskPipeline：面向异步调度的生产者—消费者执行链路重构方案

1. 执行摘要

本方案不改变 Scheduler 的一次异步前推语义，也不重写 xLLM 的模型、KV Cache、Sampler 和分布式分层；它只重构 Worker 到 Executor 之间的数据链路。

Scheduler / RPC 产生 ForwardInput，异步模式仍延迟一拍处理请求增删
→
Worker 单线程 Prepare、CPU metadata、H2D、Consume
→
Launch 线程 只做 Event、Graph/Eager/Collective launch
→
Device 完整 Prefill/Decode Task 串行执行
核心目标

移除 CPU 临界依赖

Task N 执行期间准备 Task N+1，避免在两个 Device Task 之间构造输入。

异步模式

双 Slot

同步模式 1 Slot，异步模式 2 Slot，严格保持当前只提前一个 Task。

执行约束

Launch-only

Executor 热路径不读取 CPU 数据、不动态构造 metadata、不分配输入输出 Buffer。

兼容策略

启动时二选一

Legacy 与 Prepared 新链路不热切换；Graph miss 仅回退 Prepared Eager。

结论： 方案在架构上可行。它能消除 Task 间强制串行的 CPU 输入准备；最终是否出现空泡，取决于 Prepare + H2D 是否能在前一 Task 的 Device 执行窗口内完成。

2. 背景与当前问题

2.1 当前异步调度已经具备“一步前推”

当前调度在开启 schedule overlap 后，会先提交当前 Batch，再获取上一 Batch 的真实结果。 Scheduler 使用 fake token 暂时推进状态，请求结束或取消最多额外执行一次 Task。这与目标中的 双 Slot 生产者—消费者模型在底层原理上是一致的。 

Scheduler iteration N:
  1. schedule_request()            → 构造 Task N
  2. engine.step(Task N)           → 提交 Task N，立即得到 fake output
  3. update_last_step_result(N-1)  → 获取并处理 Task N-1 的真实输出

2.2 Worker 仍承担 Task 内与 Task 间的动态输入构造

当前路径中，输入转 Device、投机验证输入构造、前一输出修正、部分 Graph 输入更新等工作分散在 Worker 和 Executor 调用前后。

  • WorkerImpl::step_async() 在工作线程执行模型调用和 overlap 修正。
  • ForwardInput::to(device) 可能动态创建和转换多组 Tensor。
  • MTP/DFlash 等路径会在 Draft 与 Target 之间继续构造验证输入。
  • 部分投机路径存在 Stream synchronize、D2H 读取和基于 Host 结果的后续输入构造。

2.3 空泡来源需要拆分

空泡类型表现本方案能否解决
Task 间 CPU 输入准备 前一 Task 结束后才开始 H2D、metadata 或 Graph 输入绑定 核心解决目标
生产者跟不上 Prepare + H2D 时间长于前一 Task 的 Device 时间 只能观测和继续优化
Eager 逐算子 dispatcher 模型内部每个算子仍需要 Host launch 不由第一阶段消除
Backend / Collective 等待 通信或 Stream 依赖造成 Device 等待 保留正确依赖，单独定位

3. 目标与非目标

首版必须实现

  • 一次完整 Prefill/Decode 作为一个 Task。
  • Worker 提前准备最终 Device 输入并提交 H2D。
  • Launch 线程只做 Device 命令提交。
  • 同步 1 Slot、异步 2 Slot。
  • Graph 与 Prepared Eager 使用同一组固定输入地址。
  • 新旧链路启动阶段二选一。
  • 固定随机种子下与旧链路确定性对齐。

首版明确不做

  • 不改变 Scheduler 的 ahead depth。
  • 不做服务期新旧链路热切换。
  • 不做通用 Patch DAG。
  • 不把完整 MTP 捕获成单个大 Graph。
  • 不同时改造所有 Device backend。
  • 不引入 Task 重试或 Pipeline 失败恢复协议。
  • 不承诺所有负载绝对零空泡。

4. 关键设计决策

Task 粒度
一次完整 Prefill/Decode；MTP Decode 包含 Draft × N、Target Validate、Rejection 和状态发布。
并发深度
同步 1 Slot，异步 2 Slot；与当前只提前一步的 Scheduler 语义一致。
线程模型
复用现有 WorkerImpl 单线程作为 Prepare/Consume 状态所有者；新增唯一 Launch 线程。
输入传递
保留 const ForwardInput&，Prepare Ack 前短期借用，不复制完整 ForwardInput。
输出语义
同步 Future 返回真实输出；异步 Future 只表示提交成功，真实输出由 get_last_step_result() 唯一消费。
Graph 策略
Graph replay miss 可回退 Prepared Eager；不允许运行时回退 Legacy Worker 链路。
错误语义
首版保持当前 fail-fast，不同时引入 Task 级恢复、重试和跨 Rank 错误协议。
首版范围
NPU；普通 LLM、MTP、Eagle3。DFlash/DSpark 作为同架构后续阶段，Suffix 保持 Legacy。

5. 总体架构与分层

Worker                              （外部接口与启动期分流）
├── WorkerImpl* impl_               （现有模型/KV/Sampler/Legacy step_async）
└── PreparedTaskPipeline            （新增组合组件）
    ├── PreparedTaskAdapter         （LLM/MTP/Eagle3 固定 Task 函数）
    ├── ExecutionSlot[1 or 2]
    ├── ready_queue                 （Worker → Launch，SPSC）
    ├── completed_queue             （Launch → Worker，SPSC）
    ├── output_fifo                 （Consume 后的有序 Host 输出）
    └── Launch thread

PreparedTaskAdapter
└── PreparedExecutor               （NPU 首版能力接口）
    ├── PreparedInputArena[slot_count]
    ├── Graph binding
    └── Prepared Eager binding

5.1 Worker 作为组合拥有者

PreparedTaskPipeline 放在外层 Worker，而不是塞进 WorkerImpl 基类， 也不分别复制到 LLM/MTP 子类。这样 Legacy 的 WorkerImpl::step_async() 可以保持原样。 

Worker::step_async(input) {
  if (prepared_pipeline_ != nullptr) {
    return prepared_pipeline_->submit(input);
  }
  return impl_->step_async(input);  // Legacy 原路径
}

5.2 单状态所有者

Slot 状态、Prepare 和 Consume 只由 WorkerImpl 单线程修改。RPC、SHM polling、Launch 线程都不能直接重排或回收 Slot。 Launch 线程只进行 READY → RUNNING → COMPLETED 所需的 Device 提交，并通过 CompletionTicket 返回结果。

6. ExecutionSlot 与队列

FREE→ PREPARING→ READY→ RUNNING→ COMPLETED→ CONSUMING→ FREE
READY 的准确含义： Host 已完成所有运行所需的描述符构造，H2D 已提交，输入不可再由 Host 修改；但 H2D 可以仍在进行， Launch 通过 Event 在 Device Stream 上建立依赖。

6.1 Slot 主要内容

Pipeline 通用字段

  • slot_id 与 Debug-only task_seq_no
  • TaskKind
  • h2d_ready_event
  • task_output_event
  • host_output_ready_event
  • reuse_fence
  • 最小 Host source lease

Adapter / Executor 字段

  • PreparedInputArena lease
  • 固定 Invocation binding
  • 算法专属 DeviceStepState
  • predecessor_row Device 映射
  • 最小 D2H 输出 Buffer

6.2 有界 SPSC

  • ready_queue：唯一生产者为 Worker 状态线程，唯一消费者为 Launch 线程。
  • completed_queue：唯一生产者为 Launch 线程，唯一消费者为 Worker 状态线程。
  • 容量与 Slot 数一致；首版不设计超过一步的可配置 ahead depth。
  • task_seq_no 仅用于 Debug FIFO 断言，不进入 RPC、ForwardInput 或 Release 热路径。

7. 单次异步 Decode 时序

Scheduler
构造 Task N 等待 Prepare Ack GetLast(N-1) 处理真实输出
Worker 线程
Prepare N H2D enqueue N READY + Ack Consume N-1
Launch 线程
取 READY N 提交完整 Task N 提交 D2H
Device
Execute N-1 Execute N

7.1 Prepare Ack

Prepare Ack 在以下条件全部满足后返回：

  1. 所有 CPU metadata 已构造或复制到 Slot 所有的存储；
  2. 所有输入 H2D 已提交到 prepare_stream；
  3. 已记录 h2d_ready_event；
  4. 异步 DMA 源由 Slot 持有，原始 ForwardInput 不再被访问；
  5. Task 已发布为 READY。

Ack 不等待 H2D 完成，也不做 Host synchronize。

7.2 Future 语义

模式step_async() Future真实输出入口
同步 / 1 SlotTask Consume 后返回真实 ForwardOutputFuture
异步 / 2 SlotPrepare Ack 后成功结束，不承载真实输出get_last_step_result()

8. 输入准备、H2D 与所有权

8.1 保持 const 引用接口

step_async(const ForwardInput& input)
  → enqueue PrepareCommand{&input}
  → calling thread waits Prepare Ack
  → Worker never accesses input after Ack

该设计不深拷贝整个 ForwardInput，也不要求把所有上层接口改成按值或右值传递。 Ack 等待替代了原实现中调用方同步执行 prepare_work_before_execute() 的生命周期保证。

8.2 Host source lease

Slot 只保留异步 DMA 真正需要的 Host 资源：

  • Pinned packed input buffer；
  • 可能跨 Ack 继续被 DMA 读取的 Tensor storage；
  • 来自 SHM、可能被下一 step 覆盖的必要稳定副本。

首版允许复用当前稳定化逻辑，但目标是将逐 step clone() 收敛为 Slot 级可复用 Pinned Staging Arena， 并用 prepare_cpu_latency 和 Host allocation 指标判断是否需要进一步重构 Scheduler 输出格式。

8.3 Stream 与 Event

prepare_stream

Worker 提交 H2D 和不依赖前驱 Device 输出的输入更新。

task_stream

完整 Task 串行执行。Task 内 Draft、Target、Patch 和通信均按顺序提交。

result_stream

等待 Task 输出 Event 后提交最小 D2H，不阻塞下一 Task 的 task_stream。

同一 task_stream 内依赖使用 FIFO；只有跨 Stream 才使用 Event。 Device Event wait 是 Stream 依赖命令，不是计算 Kernel，也不能退化为 Host synchronize。

9. Adapter 与 PreparedExecutor

9.1 三阶段 Adapter

class PreparedTaskAdapter {
 public:
  virtual TaskKind classify(const ForwardInput&) = 0;

  virtual void prepare(const ForwardInput&,
                       ExecutionSlot&,
                       PrepareContext&) = 0;

  virtual void launch(ExecutionSlot&,
                      LaunchContext&) = 0;

  virtual ForwardOutput consume(ExecutionSlot&) = 0;
};
  • Pipeline 只管理 Slot、队列、生命周期和 Promise。
  • Adapter 只描述一次完整 Task 的固定逻辑调用。
  • Graph/Eager、ACL 类型、Graph cache 和 Arena 绑定都封装在 Executor 侧。

9.2 独立 PreparedExecutor 能力

不直接扩展所有现有 ExecutorImpl，避免其他 backend 被迫提供空实现。

class PreparedExecutor {
 public:
  virtual PreparedSlotBinding bind_prepared(
      int32_t slot_id,
      int32_t invocation_index,
      const PreparedInvocationDescriptor& descriptor) = 0;

  virtual void launch_prepared(
      const PreparedSlotBinding& binding,
      Stream& task_stream) = 0;
};
边界说明： bind_prepared() 在 Worker Prepare 阶段调用，可以进行 CPU key 计算和绑定； launch_prepared() 才属于 Executor 消费热路径，必须是 launch-only。

9.3 Launch 阶段允许与禁止

允许

  • 固定 switch / for
  • Stream Event wait / record
  • Graph replay
  • Prepared Eager 算子提交
  • Collective / broadcast launch
  • 框架 dispatcher 必需的 Host 控制

禁止

  • .item()、D2H 读取或 Host synchronize
  • 依据 Device 数据做 CPU 分支
  • 动态构造 metadata 或替换 Tensor 字段
  • 运行期分配输入输出 Device Buffer
  • 修改 Scheduler、Request 或 BlockManager

10. Graph 适配

10.1 统一最终输入 Arena

PreparedExecutor
└── PreparedInputArena[slot_count]
    ├── Slot 0: tokens / positions / block tables / sampling / state
    └── Slot 1: tokens / positions / block tables / sampling / state

Worker 直接 H2D 到最终 Arena。Graph 和 Prepared Eager 都消费这些地址，不采用 “ExecutionSlot Buffer → Graph persistent Buffer”的整份 D2D 路径。

启动期为字段选择固定布局策略：

  • DIRECT_BIND：Graph/Eager 直接绑定 Arena 字段；
  • DEVICE_PATCH：由前驱状态生成或修正少量字段；
  • DEVICE_PACK：确有布局变换需求时，由固定 Kernel 写最终地址。

10.2 显式 Slot，而不是隐式轮转

Legacy ACL Graph 继续保持当前 next_replay_slot_ 隐式轮转。 Prepared 新路径显式传入 slot_id，一次 MTP Task 中 Draft 与 Target 必须使用同一个逻辑 Slot： 

Task(slot=0):
  draft_graph.bind(slot=0)
  target_graph.bind(slot=0)

Task(slot=1):
  draft_graph.bind(slot=1)
  target_graph.bind(slot=1)

10.3 Graph fallback

  • Prepare 阶段计算 Graph key、查询启动期已捕获的 Graph 并绑定。
  • Graph miss 只影响单次模型 Invocation，可回退 Prepared Eager。
  • 一次 MTP Task 可以出现 Draft Graph × N → Target Eager。
  • 服务期间不做 lazy/background capture。
  • 不允许运行时从 Prepared Pipeline 回退 Legacy Worker 执行。

11. LLM 与 MTP 固定执行路径

11.1 顶层 TaskKind

enum class TaskKind {
  PREFILL_LIKE,  // PREFILL / CHUNKED_PREFILL / MIXED
  DECODE,
  EMPTY,
};

算法类型由启动时选择的 Adapter 决定，不在 Task 热路径增加 MTP/Eagle3/DFlash 类型判断。

11.2 普通 LLM

LLM PREFILL_LIKE / DECODE:
  wait(h2d_ready_event)
  → model forward
  → lm_head / sampling
  → publish LLMPreparedState
  → result D2H

11.3 MTP Prefill

Target Prefill
→ Target lm_head / Sampling
→ Device Patch：token + embedding
→ Draft Prefill
→ Draft 状态更新
→ 发布 MTPPreparedState

Target 输出不能先 D2H 再由 CPU 构造 Draft Prefill 输入。Target token 和 embedding 必须在 Device 上直接写入 Draft 的最终 InputArena。

11.4 MTP Decode

Task continuation patch
→ Draft step 0
→ MTP_NEXT_DRAFT patch
→ Draft step 1
→ ...
→ Draft step N-1
→ MTP_TARGET_VERIFY patch
→ Target Validate
→ Rejection Sampling
→ MTP_PUBLISH_STEP_STATE
→ 最小结果 D2H

固定语义入口：

TASK_CONTINUATION
MTP_PREFILL_TO_DRAFT
MTP_NEXT_DRAFT
MTP_TARGET_VERIFY
MTP_PUBLISH_STEP_STATE

常用路径争取融合为单 Kernel；特殊路径可以是固定小型 Kernel 序列。首版不设计通用 Patch DAG。 当前 mtp_async_input_builder.cpp 中运行期的 arange/stack/to/zeros_like 等动态 Device Tensor 操作需要改造成预分配输出与固定 Patch。

11.5 EMPTY

EMPTY 仍需参加必要的分布式 collective。输入使用启动期固定 fake input，不在 Launch 阶段临时创建 Tensor。

12. 其他投机算法适配

算法Task 拓扑适配判断计划
Eagle3 MTP 拓扑；Target aux hidden 为 3H，并做 draft→target token 映射 无架构性障碍，可复用 MTP Adapter 主体 阶段 5
DFlash 一次 Block Draft → Target Validate → Context-KV 写入 需移除当前 Validate 后 D2H/synchronize，并在 Device 生成 Context-KV 写入索引 阶段 6
DSpark DFlash + 固定 N 轮 Markov sampling / broadcast 固定循环可 launch-only，但需预分配循环 Tensor 和 Sampling descriptor 阶段 6
Suffix CPU suffix tree 根据上一 Task 的真实接受 token 生成下一组 Draft 与完整提前 Prepare 存在根本依赖；除非将 suffix cache/search 迁移 Device 保持 Legacy
Suffix 为什么不能直接接入： Task N+1 的 CPU suffix 查询必须等待 Task N 的真实接受 token，而异步 Pipeline 要在消费 N 之前完成 N+1 Prepare。 使用旧历史会改变提案语义，等待 D2H 则重新引入 Device 空泡。

13. 跨 Task Device 状态与 KV Block

13.1 predecessor_row

请求在相邻 Task 间可能新增、删除和重排，不能假设 row index 保持不变。

Task C row 0 ← Task B row 0
Task C row 1 ← Task B row 2
Task C row 2 ← -1              // NEW_REQUEST

映射由 Scheduler/Batch 构造 ForwardInput 时顺手生成，避免 Worker 再做 request_id 字符串哈希扫描。 Device Patch gather 继续请求的状态；新请求保留 Worker 已写入的初始值。

13.2 Adapter 专属 DeviceStepState

LLMPreparedState

  • next token
  • sampled row
  • valid mask

MTPPreparedState

  • accepted tokens / accepted length
  • tail token / previous token
  • tail embedding / previous embedding
  • position offset

Eagle3 使用 3H embedding 布局；DFlash/DSpark 后续定义 Context-KV 专属状态。Pipeline 不解释这些字段，只持有 Slot 与 Event。

speculative Publish 必须提交完整 verify width，而不是只提交当前有效前缀；第 0 列始终有效，后续无效列必须构成连续 suffix。 因而单步 accepted length 的闭区间为 [1, verify_width]。Host 模板已经包含第 0 个提交 token，前驱状态相对模板的 额外推进量仅为 [0, verify_width - 1]，所以 expanded Target Verify 使用 q_max_seq_len - 1 作为 KV plan headroom。MTP/Eagle3 与 DFlash/DSpark 的 State Publish 均强制输入 width 精确等于启动期 accepted_token_capacity；MTP Backend 还要求该容量精确等于模型最大 verify width，避免容量、 Arena 布局和 attention plan 上界发生静默偏差。

DeepSeek-V4 multi-manager 的下标语义固定为“存在的角色按 SWA → C4 → C128 排列”。Scheduler 导出、 Engine manager 初始化、模型 group_infos 与 Prepared Device staging 必须使用同一顺序；缺少某个 compression role 时允许跳过该角色，但不允许改变剩余角色的相对顺序。metadata builder 会拒绝 C128-before-C4、重复 ratio、非 token compression group 或非 SWA 的 manager 0，Prepared Block-Spec 还要求输入 manager 数量精确等于 Target 模型的角色集合。

13.3 KV Block 生命周期

  • Scheduler/BlockManager 仍是唯一分配者。
  • Device Patch 只消费已准备好的 block table，不申请 Block。
  • 已提交 Task 引用的 Block 必须延迟释放，直到对应 Slot 安全退休。
  • Executor 不参与 Block 分配、抢占或回收决策。
  • 复用现有 schedule-overlap lookahead 最坏情况预留，覆盖最多额外执行一个 Task。

13.4 reuse_fence

后继 Task 读取完前驱 DeviceStepState 后，在 task_stream 记录 reuse_fence。 Slot 再次进入 PREPARING 前，prepare_stream 等待该 Fence；Host 不同步等待。

14. 显存与 Buffer 规划

14.1 双 Slot 只复制跨 Task 并存数据

  • Draft / Target 最终输入 Arena；
  • block table、predecessor mapping；
  • 算法专属 DeviceStepState；
  • 最小 Device/Host 输出；
  • Event 与 backend 必需的 slot-local Graph pool。

14.2 Task 内共享一份串行 Workspace

  • N 轮 Draft 历史与临时 logits；
  • Target logits；
  • Rejection scratch；
  • activation、sampling、communication workspace。
Prepared memory ≈
  slot_count × (input arena + step state + minimal result)
  + one shared task workspace
  + backend-required graph-local pool

不保存 N 份完整 ForwardOutput，不在运行期扩容 Device Buffer。所有上限由启动配置的最大 batch、最大 token、 block-table width 和 speculative width 推导。

15. 输出、D2H 与 Consume

task_stream records task_output_event
→ result_stream waits task_output_event
→ async D2H into slot-local pinned output
→ host_output_ready_event
→ CompletionTicket
→ Worker Consume
→ output_fifo
→ get_last_step_result()
  • 只 D2H Host 真正需要的数据；DeviceStepState 不为下一 Task 做 D2H。
  • Worker 等待 Host output Event、转换输出并回收 Slot。
  • 首版不增加 completion thread、Host Callback 或忙轮询。
  • 异步正常 Consume 由 get_last_step_result() 驱动。
  • WorkerService 的 fake-token 行为和外部 RPC 接口保持不变。
关键顺序： Worker 必须先把 Task N 发布为 READY，再等待和消费 Task N-1。这样 Host Consume 与 Device Execute(N) 重叠， 不会阻塞两个 Device Task 之间的提交。

16. 生命周期与错误语义

16.1 固定配置下复用同一 Pipeline

CREATED→ RUNNING↔ QUIESCENT→ STOPPED
  • quiesce()：pause/preempt 前通过正常 GetLast 收回在途 Task，使所有 Slot 回到 FREE。
  • resume()：重新开放同一个 Pipeline，不重新分配 Arena、不重绑 Graph。
  • shutdown()：停止新 Task，安全退休已提交 Device 操作并销毁资源。
  • 不设计通用 DrainPolicy，也不向 TaskKind 添加 STOP/DRAIN 控制 Task。

16.2 首版保持 fail-fast

当前 xLLM 大量使用 CHECK，ThreadPool runnable 也没有统一异常捕获与 Promise 错误传播。 本次性能数据链路重构不同时扩展为 Task 重试或 Pipeline 恢复项目。

  • Prepare、Launch、Device、Collective、Consume 的非预期错误记录 Task 阶段与 Slot 后 Fatal。
  • 不在某一 Rank 重试已可能进入 Collective 的 Task。
  • 正常请求取消、结束、Graph miss 不属于执行失败。
  • 不允许运行时切换回 Legacy 继续服务。

20.4 性能验收定义

Task N 与 Task N+1 之间不再存在必须由 CPU 串行完成的输入构造、输出读取或调度判断。 当 Prepare + H2D 能在 Execute(N) 窗口内完成时，NPU trace 中不应出现由 Host 数据准备造成的 Task 间空泡。

若仍有空泡，必须能通过上述指标区分：ready queue 为空、H2D Event 未完成、Launch/Graph replay 延迟，或 backend/collective 等待。

22. 后续：MTP 大 Graph

首版仍使用独立 Draft/Target Graph，以降低一次性重构风险。当前接口需要保证未来可以把固定 Launch 序列替换为：

mtp_big_graph[slot_id].replay();

未来大 Graph 可覆盖：

Draft × N
→ Target Validate
→ Rejection Sampling
→ DeviceStepState publish

异步双 Slot 对应同一逻辑大 Graph 的两个固定地址实例。Prefill 与 Decode 仍建议保持双 Graph，避免把不同形状和控制语义强行捕获到一个 Graph 中。

当前 PreparedInputArena、显式 slot_id、Adapter 固定 Task 函数和算法专属 DeviceStepState，都是为未来大 Graph 保留的必要接口，而不是首版直接实现大 Graph。

23. 最终结论

PreparedTaskPipeline 与当前异步 Scheduler 的底层语义一致：同步模式是单 Slot 的 CPU/Device 交替， 异步模式通过额外准备一个完整 Task，用最多一个额外 Task 的代价把 CPU Prepare 移出 Device Task 间隙。

方案的关键不是简单增加线程，而是同时建立固定输入 Arena、显式 Slot、DeviceStepState、前驱行映射和 launch-only Executor 边界。 只有这些条件共同满足，MTP 的下一步输入才能真正提前准备，Graph/Eager 才能共用数据链路，Device 空泡也才能被可靠定位和消除。

实施起点： NPU 普通 LLM + Prepared Eager + 单 Slot。默认保持 Legacy；每阶段通过确定性、内存与 NPU trace 验收后再推进。
